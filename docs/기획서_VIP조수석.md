앱명 / 프로젝트명: **VIP 조수석 (Cargo Concierge)**

## 1. 앱 한 줄 소개
케이크를 싣는 순간부터 도착해 챙길 때까지, 품목·자리 한 번 선택으로 지원되는 차량 설정·주행 코칭·설정 복원을 이어 주는 Pleos 차량용 앱입니다.

## 2. 기획 배경

**생일 케이크를 받아 든 뒤, 운전자가 해야 할 일을 줄입니다.**
케이크 상자를 조수석에 놓으면 운전자는 히터·열선을 확인하고, 코너에서 쏠리지 않게 신경 쓰고, 집에 도착하면 상자를 챙기고 공조도 되돌려야 합니다. VIP 조수석의 약속은 **물건을 위한 차량 설정부터 도착 후 정리까지 한 번의 선택으로 이어 주는 것**입니다. 18℃ 공조 설정이나 낮은 G만으로 케이크가 보호됐다고 판정하지 않고, 적용된 항목과 확인하지 못한 항목을 구분합니다.

VIP 조수석은 이 과정을 **‘물건과 자리 선택 → 지원되는 설정 적용 → 쏠림 코칭 → 도착 챙김 → 설정 복원’**이라는 하나의 보호 세션으로 묶습니다. 물건의 상태를 센서로 직접 판정하거나 파손을 막는 제어장치가 아니라, 운전자가 적재물을 고려해 차량을 쓰도록 돕는 보조 앱입니다. 자동차의 조향·제동·가속을 직접 제어하지 않습니다.

**첫 경험은 케이크, 반복 사용은 퇴근길 포장음식입니다.** 1차 타깃은 빈 조수석에 픽업한 물건을 싣는 Pleos 탑재 차량의 가족 운전자입니다. 수도권 30~40대 맞벌이 부모가 주 1~2회 포장음식, 주 1회 장보기, 분기 1~2회 케이크·꽃을 운반한다는 것은 팀의 고객·빈도 가정(D)입니다. 케이크로 사용법을 익힌 뒤 다음 주 포장음식을 최근 VIP에서 골라 코칭·챙김을 다시 쓰는지를 검증합니다. 반복 사용 검증은 열선 보온의 효과와 분리해, 공조를 바꾸지 않는 사용도 포함합니다.

매일 앱을 열게 만드는 것이 목표는 아닙니다. **물건을 싣는 날에 적절히 제안하고, 사용하지 않을 때는 조용히 있는 것**이 재사용의 조건입니다. 따라서 설치 수뿐 아니라 제안이 실제 선택으로 이어지는 비율, 보호 세션 완료, 불필요한 제안으로 끈 비율을 함께 봅니다. 현재 도어 기반 제안은 앱이 신호를 수신하는 동안 동작하며, 시동 전 이력·저장 매장 지오펜스·백그라운드 자동 호출은 추가 연동과 정책 확인이 필요한 확장 범위입니다.

**차량 앱의 필수성이 생기는 지점.**
- 차량 내부의 도어·기어·차속·착좌 신호를 이용해 ‘지금 싣는 중인지, 사람이 앉아 있는지, 출발했는지’를 한 흐름에서 판단할 수 있습니다. 도어가 닫혔다는 이유만으로 적재물을 확정하지 않고 사용자의 품목 선택을 받습니다.
- Pleos Vehicle SDK로 지원되는 좌석 온도·열선·통풍을 요청하고, 항목별 적용 결과를 보여줄 수 있습니다. 같은 차 안에서도 조수석 단독 존과 운전석을 포함한 공유 존을 구분하는 것이 핵심입니다.
- 차속·조향각으로 관성의 크기를 추정하고 차량 화면·스피커로 코칭을 전달합니다. 실제 센서 대비 선행 시간·정확도 결과는 현재 제출 자료에 포함되지 않아 성능 수치로 주장하지 않습니다.
- 내비 도착과 P단·운전석 도어를 연결해 챙김과 복원을 이어갑니다. 스마트폰의 가속도 기록·내비 안내와 비교할 차별점은 ‘측정 자체’보다 **좌석 제어와 이동 전후의 처리까지 묶는 차량 내부 연동**입니다.

**왜 Pleos인가.** 현재 구현은 Pleos Vehicle 2.3.2, NaviHelper 3.0.5, FusedLocation 1.1.3, TTS/STT 3.3.1 어댑터를 사용하며, 공식 Pleos Connect v2.1 에뮬레이터에서 실행·제어를 확인했습니다. 별도의 적재물 센서나 서버를 먼저 구축하지 않고 차량 플랫폼이 제공하는 정보로 사용 흐름을 검증할 수 있습니다. 에뮬레이터에서의 성공이 모든 실차의 권한·좌석 구성·앱마켓 승인을 뜻하지는 않으며, 그 차이를 5항에 구분했습니다.

**기존 방식과 비교할 제품 가치.** 아래 비교는 개별 서비스의 모든 기능을 조사해 독점성을 주장하기 위한 표가 아니라, 우리가 제공하려는 사용 단위를 설명한 것입니다.

| 기존 방식 | 사용자가 직접 맡는 일 | VIP 조수석의 제안 |
|---|---|---|
| 차량 공조·시트 수동 조절 | 물건에 맞는 항목을 골라 변경하고 나중에 복구 | 품목·자리 선택에 설정 요청을 묶고 적용 여부 표시, 도착 시 저장값으로 복원 요청 |
| 일반 음성 차량 제어 | 온도·열선 등 개별 명령을 구성하고 종료 시점 기억 | ‘케이크 실었어’처럼 품목·자리를 입력해 세션 시작. 현재는 앱 내 STT, Gleo 호출어는 향후 연동 |
| 급가감속 기록·운전 점수 | 주행 뒤 기록을 보고 개선점을 해석 | 적재물별 초기 한계값으로 이동 중 짧게 코칭하고 도착 후 최대 추정 G·횟수 확인 |
| 보냉백·완충재·적재 고정 | 물건을 물리적으로 보호 | 이를 대체하지 않고, 적재 후 공조 사용·운전 습관·챙김을 보조 |

**성공의 기준.** 케이크가 멀쩡했다는 한 번의 장면보다, 사용자가 선택한 자리만 제어되고 미지원 기능은 정직하게 표시되며 종료 후 복원이 확인되는 경험을 우선합니다. 보호 효과의 크기, 알림 피로, 재사용 의향은 별도의 측정·사용자 검증으로 판단합니다.

## 3. 앱 주요 기능 및 차량 특화 요소

**심사에서 볼 핵심은 한 가지 흐름입니다.** 케이크·조수석 선택 → 항목별 적용 상태 → 주행 코칭 → 도착 챙김·복원입니다. 보호 분류는 9종이며 대표 시연은 케이크에 집중합니다. 반복 사용은 포장음식으로 확인합니다.

- **핵심:** 정차 수동 선택·최근 VIP, 지원 상태 표시, 유효한 차속·조향 입력을 사용하는 코칭, 챙김·종료 상태 확인.
- **조건부:** 도어 제안은 앱이 신호를 받는 동안, 공조·시트는 독립 존·권한·차량 허용 범위에서 동작합니다. 열선 ON은 검증 전 차단하며, 반려동물 분류는 별도 적합성 검증 대상으로 둡니다.
- **향후:** Gleo 호출어, 저장 매장·지오펜스, 부팅 전 도어 이력, 실제 내비의 선행 코칭, 영구 리포트·공유는 연동·검증 후 확장합니다.

아래 ‘현재 구현’은 소스와 제출 APK의 범위입니다. 앱 로직 검증, 에뮬레이터 SDK 호출, 실차 효과는 서로 다른 증거로 구분합니다.

리포트의 횟수는 앱 정책이 허용한 주행 안내 요청 수이며 실제 스피커 재생 완료 횟수가 아닙니다. 음소거·TTS 가용성과 순정 내비의 소리는 사용성 시험에서 따로 확인합니다.

**분류별 초기값과 실제 요청.** 모든 한계 G는 물건의 안전을 보증하는 임계값이 아니라 코칭을 시작할 초기 가설입니다. 문헌은 참고 범위, 물리식은 단순화된 설명이며, 실제 포장·고정·시트 재질에 따른 차이는 5항의 실측으로 보정합니다. 근거 등급은 A=공식 자료·직접 측정, B=문헌·지침, C=물리 유도, D=팀 가정입니다.

**제어 경계와 실패 시 행동.**
- 기본 진입은 정차 화면의 사용자 선택이며, 최근 VIP·추천 품목에서 바로 선택할 수 있습니다. 주행 또는 AAOS UX 제한 시 정적 배지로 바꾸고 목록·설정 조작을 숨깁니다. 제어 큐에서 실행 직전 상태를 다시 확인하고, 오래된 적용 요청과 이전 세션의 늦은 결과를 현재 세션에 반영하지 않도록 보완했습니다.
- 적용 결과가 ‘미지원·권한 없음·실패’이면 그 항목의 보호 효과를 주장하지 않습니다. 에뮬레이터의 공유 풍량·풍향은 유지합니다. 차속 수신이 오래됐으면 추정을 멈추며, 조향만 만료되면 횡G를 제외하고 가감속만 추정한다고 표시합니다. 이 신선도 확인이 원천 센서의 정확도를 보증하지는 않습니다.
- 열선 ON 요청은 기존 동의 여부와 무관하게 ‘검증 대기’로 차단합니다. 30분 감열·45분 종료 같은 미검증 시간을 안전 기준으로 구현하지 않습니다. OCS 제한을 우회하거나 온풍으로 자동 대체하지 않고, 보온 없이 지원되는 코칭·챙김을 사용합니다.
- 사람이 이미 앉은 자리를 사용자가 선택하면 열선·통풍 요청을 빼고 시작합니다. 비어 있던 VIP 자리에 새 착좌가 생기면 좌석을 사용하는 프리셋은 종료·복원 요청을 합니다. 착좌 센서는 사람과 무거운 짐을 항상 구별하는 증거가 아니므로 실제 적재 위치 확인은 사용자에게 남습니다.
- 종료 시 복원을 요청하고 결과에 맞춰 상태를 표시합니다. 원래 값이 없거나 외부 변경이 관찰된 항목을 임의 값으로 덮어쓰지 않는 것이 제어 원칙입니다. 앱 비정상 종료 후에는 미완료 표식으로 확인을 요청하며, 저장값 자동 복구를 보장하지 않습니다. 실행 중 복원 실패는 새 적용을 보류하고 P 정차 후 재확인 버튼을 제공합니다. 프로세스 종료 후 자동 복구와 읽기·쓰기 사이 외부 변경 경쟁은 5항의 추가 검증 범위입니다.
- 공조·시트는 냉장·온장 설비가 아닙니다. 포장 상태와 품목에 맞는 보냉·보온 수단, 적재 고정, 이동장 사용이 우선입니다. 열선의 식품 보존 효과와 단열 포장 조합은 검증 전이므로 일반 사용자를 대상으로 장시간 자동 보온을 권하는 단계가 아닙니다. 브레이크·조향·구동 제어와 자율주행 기능은 범위에 없습니다.

**개인정보와 사용 기록.** 앱 자체 서버와 외부 분석 수집 모듈은 현재 구조에 없습니다. 최근 VIP 이름·분류와 설정은 차량 로컬에 저장되고 지울 수 있습니다. 인식한 음성 텍스트는 UI·진단 로그에 나타날 수 있으므로 ‘텍스트를 전혀 보관하지 않는다’고 표현하지 않습니다. 리포트는 현재 세션 화면에서 확인하며 영구 이력 저장·이미지 공유는 확장 계획입니다. Pleos 음성·위치 서비스 자체의 데이터 처리와 권한 정책은 플랫폼 범위로 구분합니다. 향후 사용성 검증을 위한 로그 제공은 참여자의 별도 동의와 최소 항목 수집을 전제로 설계합니다.

## 4. 주요 사용 시나리오

**시나리오 A — 케이크를 조수석에 싣고 귀가.** 현재 제출본을 대표하는 흐름입니다.
1. 운전자는 P단으로 정차한 상태에서 앱을 열고 케이크 상자를 조수석 시트 위에 안정적으로 놓습니다. 조수석 문을 열었다 닫으면 ‘오늘의 VIP’ 화면이 나타납니다. 앱이 시작되기 전 도어 이력은 현재 자동 연결되지 않으므로, 이미 실은 뒤 앱을 열었거나 제안이 억제된 경우 홈에서 직접 케이크를 선택합니다.
2. 케이크와 조수석을 확인하면 0.15G 가드가 시작되고 조수석 18℃·열선 OFF 등의 요청 결과가 표시됩니다. 온도 변경이 적용되고 풍량·풍향이 ‘공유 존 유지’라면, 그 상태 그대로 출발 여부를 판단합니다. 18℃는 공조 설정값이며 케이크 상자 내부가 그 온도가 됐다는 뜻은 아닙니다.
3. 출발하면 정적 배지로 바뀝니다. 차속·조향각에서 계산한 G가 한계의 80% 구간에 진입하면 효과음, 초과하면 짧은 음성 코칭을 합니다. 운전자는 교통 상황을 우선하면서 가능한 구간에서 부드럽게 조작합니다. 실제 케이크의 상태를 확인하거나 손상을 판단하는 기능은 없습니다.
4. 내비가 먼저 도착을 알렸는데 아직 D단이면 앱은 챙김을 예고합니다. 이후 P단·정차, 또는 P단·정차에서 운전석 문 열림 시 챙김 안내·복원 요청·리포트를 제공합니다. 운전자는 케이크를 챙기고 복원된 공조·시트 상태를 확인합니다.
5. 종료 화면의 복원 결과와 순정 공조 상태를 확인합니다. 요청만 전달됐거나 확인에 실패한 항목은 완료로 간주하지 않습니다. 기존 v1.0.0 영상은 당시 동작 기록이며 보완된 실패 처리의 증거와 구분합니다.

**시나리오 B — 뜨거운 포장음식을 싣는 경우.**
1. 정차 화면에서 ‘조수석에 떡볶이 실었어’라고 말하면 별칭 사전이 뜨거운 음식으로 분류하고 0.12G 가드를 시작합니다. 인식된 이름·자리·분류가 맞는지 적재 완료 화면에서 확인합니다. 혼합 메뉴나 데우면 안 되는 포장은 사용자가 가드만 쓰는 분류를 선택해야 하며, 앱이 내용물을 검사하지 않습니다.
2. 현재 열선 ON은 기존 동의와 무관하게 검증 대기로 차단됩니다. 송풍 OFF는 조수석 단독 존이 있을 때만 적용하고 공유 존은 유지합니다. 포장음식 반복 사용은 보온 효과 없이도 코칭·챙김이 필요한지부터 확인합니다.
3. 관성 초과 때 공통 알림 정책 안에서 코칭하고, 종료 시 지원되는 항목의 저장값으로 복원을 요청합니다. 열선 ON 차단과 복원 결과를 확인하며, 보온의 일반 사용 범위는 별도 검증 후 결정합니다.

**반복 사용·중간 정차.** 다음 주문은 정차 홈의 최근 VIP로 시작합니다. 내비 경유지만 통과하면 보호를 유지하지만 P단·정차에서 운전석 문을 열면 종료·복원을 요청합니다. 중간 매장 방문이었다면 도착 화면의 ‘잠시 정차했어요 · 같은 VIP 다시 시작’으로 새 세션을 시작합니다. 통계가 초기화되는 새 출발이며 이전 세션을 이어 붙이는 재개 기능은 아닙니다. 앱이 꺼진 동안 적재를 추적하지 않습니다.

**시나리오 C — 주말 장보기, 후석과 트렁크의 차이.**
1. 후석 문을 닫아 제안이 나타나면 신선식품을 선택합니다. 독립 후석 온도 존이 있는 차종에서는 18℃를 요청하고, 없으면 미지원 상태를 표시합니다. 운전석을 포함한 공유 존을 강제로 낮추지 않습니다.
2. 물건을 트렁크에 실었다면 차량 맵에서 트렁크를 선택합니다. 트렁크에 공조 기능이 있는 것처럼 보이지 않도록 미지원으로 처리하고 0.15G 가드·트렁크 챙김만 이어갑니다. 이미 보호 중인 물건의 자리를 옮길 때는 정차 후 변경합니다.
3. 사용자는 냉방 요청의 적용 여부를 보고 보냉·고정 수단을 함께 사용하며, 도착 시 선택한 자리의 장바구니를 챙깁니다. 상자 내부 온도 효과는 5항에서 별도 측정합니다.

**시나리오 D — 커피 캐리어, 공조가 필요 없는 사용.**
1. 드라이브스루를 나온 뒤 안전하게 정차해 커피를 선택하면 공조·시트 변경 없이 0.12G 관성 가드가 시작됩니다. 창문으로 물건을 받는 행위는 도어 이벤트가 아니므로 자동 감지를 전제로 하지 않습니다.
2. 급출발·제동·선회에서 한계를 넘는 추정치가 나오면 짧게 코칭합니다. 음료의 실제 수위·뚜껑·고정 방식은 알 수 없으므로 ‘넘침 방지 성공’ 대신 추정 G·코칭 횟수를 리포트로 보여 줍니다. 코칭이 불편하면 정차 후 음성을 끄거나 세션을 종료합니다.

**시나리오 E — 사람이 타거나 제안을 무시하는 경우.**
1. 후석에 사람이 앉아 착좌가 감지된 상태에서 문을 닫으면 해당 자리의 자동 제안을 억제합니다. 동승자가 방금 내린 경우에도 마지막 착좌 후 30초 동안 제안을 억제합니다. 이는 센서 해석에 따른 오탐 완화이며 승객 식별 기능은 아닙니다.
2. 자동 제안을 세 번 시간 초과로 넘기면 그 트리거를 일시 음소거합니다. 정차 중 품목을 수동 선택하면 무응답 기록이 초기화되며, 설정에서도 자동 제안 억제를 초기화할 수 있습니다.
3. 동승자가 꽃을 들고 있다면 운전자가 정차 중 해당 자리를 직접 선택할 수 있습니다. 앱은 ‘들고 있음’ 상태로 열선·통풍을 제외합니다. 이 모드가 안전한 적재·승차 자세를 대신하지는 않습니다.

**시나리오 F — 이름이 다른 물건과 인식 실패.**
1. ‘조수석에 도자기 실었어’는 도자기라는 이름을 유지하면서 깨지기 쉬운 물건 0.12G로 등록됩니다. ‘트렁크에 수박 실었어’처럼 사전에 없는 명사는 일반 짐 0.20G로 시작합니다. 사용자는 정차 화면에서 필요하면 분류를 바꿉니다.
2. 말이 인식되지 않으면 재입력 안내 후 화면의 품목을 선택합니다. 최근 VIP를 삭제하면 다음 제안과 음성의 우선 매칭 목록에서도 제거됩니다. 최근 목록은 편의를 위한 기능이며 품목을 자동으로 정확히 분류한다는 전제로 제어하지 않습니다.

## 5. 개발 계획

**제출 시점의 위치 — 작동하는 프로토타입과 출시 조건을 구분합니다.**
v1.1.0(versionCode 3)은 제어·복원·신호·알림과 재진입을 보완한 버전입니다. 이번 실행에서 코어 테스트 109건과 Pleos release 빌드가 통과했고, lint는 오류 0건·경고 33건입니다. 앱 모듈의 NO-SOURCE 결과는 테스트 통과 건수에 더하지 않습니다. 공식 Pleos Connect v2.1 AVD에 새 release APK를 설치·실행했습니다. 온도 원값 조회 실패는 변경 보류, 공유 풍량·풍향은 유지로 표시됨을 확인했습니다. 기존 v1.0.0 영상·단위 테스트 73건은 당시 구현의 기록입니다. 시뮬레이션 전체 코스 36개 검사 통과 역시 별도 회귀 근거이며 실차 보호 효과와 합산하지 않습니다.

**현재 구현과 버전별 검증 범위.**
- 상태머신: `Idle → Offering → Guarding → Arrived` 전환, 도어 기반 제안, 자리별 착좌·하차 직후 억제, 무응답 누적 억제, 주행 시 선택 화면 닫힘, 내비 도착 후 P단 대기, 도착 리포트. 사용자 동작과 시각을 입력으로 받아 테스트하는 구조입니다.
- 품목·자리: 보호 분류 9종, 사용자 이름과 자리 구문 파싱, 최근 VIP 로컬 저장·삭제·분류 변경, 차량 맵의 자리 선택, 동승자가 들고 있는 경우 열선·통풍 제외, 트렁크 제어 미지원 처리.
- 주행: 차속·조향각 G 추정, 차속·조향 수신 신선도 확인, 효과음·코칭·경로 안내의 공통 간격·횟수 제한, 긴급·저속 선회 억제를 보완했습니다. 차종별 보정·기준 센서 비교 결과는 별도입니다.
- 차량 연동: v1.0.0의 공식 Pleos Connect v2.1 AVD(Android 14, 2560×1440)에서 Vehicle 서비스와 기어·조향·브레이크·도어·착좌·공조 수신, 조수석 제어·정상 복원을 확인한 기록이 있습니다. v1.1.0의 종료·실패 경로는 새 검사 결과로 구분합니다. 과거 열선 호출 성공이 현재 열선 ON 허용을 뜻하지 않습니다.
- 음성·시연: Pleos TTS/STT 초기화·호출 경로와 앱 내 명령 처리, adb 데모 브리지·시나리오 재생이 있습니다. 영상의 차량 신호와 내비 이벤트 일부는 주입하며 공조·시트는 실제 SDK를 호출합니다. 영상 음성은 앱이 요청한 문장을 후처리 합성한 부분을 명시합니다. 영상만으로 실차 음성 인식률·센서 지연을 검증했다고 보지 않습니다.

## 6. 기대효과 및 발전 가능성

**다음 주에도 쓸 이유를 먼저 검증합니다.** 케이크는 첫 경험이고, 퇴근길 포장음식이 반복 사용 가설입니다. 최근 VIP로 다시 시작해 코칭·챙김·종료 확인을 이어 가는 일이 수동 설정보다 편해야 합니다. 공조를 지원하지 않는 자리에서도 이 가치가 남는지 확인합니다. 현재 자료에는 반복 사용 관찰 결과가 없으므로 파손 감소율·보관 시간 연장·연비 향상을 성과로 제시하지 않습니다.

**첫 고객과 지불 주체.** 사용자는 Pleos 탑재 자가용의 픽업 운전자, 초기 모집 채널은 픽업 매장과 차종 커뮤니티입니다. **주 지불 가설은 차량 제조사·플랫폼의 서비스 상품 담당 조직이 품목별 차량 경험을 기능 라이선스로 구매하는 것**입니다. 구매 검토자 5명 대상 인터뷰(D)를 목표로, 예산 주체·실차 검증 조건·차종 유지보수 범위·유료 파일럿 의사를 확인합니다. 접촉·계약·지불 의향이 확보됐다는 뜻이 아닙니다. 예산 주체와 유료 검증 조건이 확인되지 않으면 라이선스 매출 전망을 제시하지 않습니다.

외부 앱을 선택할 이유도 검증 대상입니다. 축적할 자산은 품목별 사용성 결과, 차종·좌석별 제어/복원 검증표, 알림 정책과 회귀 시나리오입니다. 제조사 내재화는 가능한 사업 위험이며 확인된 계획으로 쓰지 않습니다. 소비자 구독, 쿠폰 수수료, 보험 데이터 판매는 초기 모델에서 제외합니다. 반복 운반 사업자·PBV 센서 연동판은 후속 수요 검증으로 두며, 기존 대당 월 1만 원(D)은 그 별도 확장판의 미검증 가격 가설입니다.

**QR부터 차량까지의 진입 동선.** 매장 QR → 휴대폰의 지원 차종·기능 안내 → 사용자가 차량에서 Pleos App Market의 앱을 찾아 설치 → 정차 중 품목·자리 선택 → 첫 세션 종료·상태 확인을 계획합니다. 휴대폰에서 차량으로 원격 설치·자동 전송되는 연결은 확인되지 않아 전제하지 않습니다. App Market 등록·차량 검색 경로가 확인되기 전에는 동의한 참여자의 시험 환경에서 안내 동선을 검증합니다. QR 스캔이나 안내 페이지 조회를 차량 설치로 세지 않습니다.

**첫 1,000의 정의와 확보 조건.** 목표는 마켓 배포 가능 시점부터 8주간 **서로 다른 지원 차량 1,000대의 설치**입니다(D). 동일 차량의 재설치·중복 채널 유입은 한 대로 셉니다. 아래 산술에서 ‘유효 노출’은 지원 차량을 가진 참여자에게 설치 안내가 도달한 첫 노출을 차량 단위로 중복 제거한 값이며, 불특정 광고 조회 수와 다릅니다.
- 유효 노출 → 차량 설치 3%, 설치 → 첫 세션 완료 60%는 팀 가정(D)입니다. 이 가정에서 1,000대 설치에는 약 33,333대분의 유효 노출(정수 올림 33,334)이 필요하며, 첫 완료 차량은 계산상 600대입니다.
- 목표가 **첫 세션 완료 차량 1,000대**라면 유효 노출은 약 55,556대분, 설치는 계산상 약 1,667대가 필요합니다. 설치 목표와 완료 목표를 같은 ‘사용자 1,000명’으로 부르지 않습니다. 계산은 유입 전망이나 확보 실적이 아닙니다.
- 매장 2곳·차종 커뮤니티 1곳의 2주 탐색 파일럿(D)에서 채널별 지원 차량 접점, 안내 동의, 차량 설치, 첫 완료를 측정합니다. 접촉 목표이며 확정 제휴가 아닙니다. 채널별 확보 가능량은 현재 미확인으로 남겨 두고, 중복 제거한 노출 공급량이 8주 목표를 지지하지 않으면 기간·목표를 조정합니다. 마켓 추천 노출은 승인과 노출량을 확인한 뒤 별도 산정합니다.

**측정 지표의 정의.** 현재 앱에는 외부 분석 수집 모듈이 없습니다. 초기 측정은 별도 동의한 관찰·설문과 최소한의 기기 내 기록으로 진행하고, 수집 항목·보관 기간·철회 방법을 먼저 정합니다. 사람·차량·세션의 분모를 섞지 않습니다.

**규모 추정은 보조 시나리오입니다.** 2027년 말 국내 Pleos 탑재 차량 28만 대, 운반 가능 사용자 차량 70%인 19.6만 대는 기존 팀 가정(D)입니다. 과거 그랜저 전체 판매량을 지원 차량 수로 치환하지 않으며 제조사 전망·확정 보급 대수로 사용하지 않습니다. 실제 차종·트림·권한·시장 자료가 확보되면 모수를 교체합니다.
